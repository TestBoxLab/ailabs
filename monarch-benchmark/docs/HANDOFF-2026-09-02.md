### 2. First feature to spec: declarative benchmark configuration

Today everything is CLI flags (`wb run --suite ... --arms ... --k ...`) plus code (provider registry,
side-effect list, audiences.yaml). Carlos wants the benchmark to be driven by declarative files instead.
Brainstorm first; the shape below is his input, not a decision.

A **target** file (one per target) declaring:
- the platform under test: the simulated API set, a real platform with API + UI, or a real API-only service;
- the data: which synthetic dataset or tenant, and whether the benchmark may modify it (read-only vs mutable);
- which Monarch stages are under test: full flow (discovery + creation + execution), creation + execution, execution only;
- how to reach Monarch: base URL, credentials or access token, release version;
- the task corpus (prompt set) for that target and the per-service side-effect list used for contracts.

A **run** file declaring competitors, trials (k), timeout, concurrency, audience, cost ceiling.

The CLI then becomes thin: `wb run <run-file>` (and the same file drives the CI workflows). Keep the fixed
methodology in `PLAN.md` §1 unchanged; only its inputs become files.

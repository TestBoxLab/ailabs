1. In one minute

Lucas designed and partly built a benchmark for Monarch. The benchmark gives the same task (for example, "read Lisa's email and update her city in Salesforce") to several competitors: Monarch, and off-the-shelf AI models or agents. It then checks who did the task correctly, how much it cost, and how long it took.

The tasks run against a simulated set of 47 business apps (Salesforce, Gmail, Asana, HubSpot and so on) borrowed from Zapier's open-source AutomationBench. Simulated means: no real accounts, fully predictable, and each task costs cents. A version against real accounts is designed but not built yet.

What exists today: the simulated apps, the checker that decides pass or fail, a runner that can be interrupted and resumed, a results database, statistics, a report generator, and 200 tasks. One real model (Kimi K3) has been run. Monarch itself has never been run through it. That was blocked on two questions to Deyton. Reading the Monarch code today answers both, and reveals a third problem (section 8).

4. How the benchmark works

Each test is one task given to one competitor. The simulated apps are loaded with the task's starting data (an inbox, a few CRM contacts). A snapshot is taken. The competitor works. A second snapshot is taken. The checker compares the two snapshots. The checker runs separately, after the competitor has finished, so nothing grades its own work.

The checker

A task passes only if both of these hold:

  • The expected result is there. Example: contact 003004 now has city = Denver.
  • Nothing else changed. Every change between the two snapshots must be either expected or explicitly allowed. This catches a competitor that does the task but also deletes an email on the way.

There is also a sanity rule for the tasks themselves: every check must fail on the untouched starting data. Otherwise the task is empty. This runs automatically in CI.

The first pilot showed why the second rule matters: a scripted "sloppy" competitor that does the task plus one unwanted change passes 100% of the "expected result" checks and only gets caught by the "nothing else changed" rule, dropping to 40%.

Competitors

The documents call them "arms". Each one has a fixed configuration and a versioned name, so results are comparable over time.

CompetitorWhat it isWhy it is there

5. What we test, and against what

Two separate questions, easy to mix up:

5.1 Which platform is the target?

Monarch's job is to map a platform and then operate it. The benchmark can point at different kinds of platform, and each kind needs its own set of task prompts:

Target platformExampleWhat makes it differentStatus
Simulated API setThe AutomationBench mock of 47 appsNo UI. Endpoints are described in files. Predictable, cheap.Today's target
Real platform with API and UISalesforce, HubSpot, Asana, LinearMonarch can map it from the UI and from network traffic. Needs a test account, cleanup between tasks, and a check of the vendor's terms.Later
Real platform, API onlyA public REST API with no web appOnly the API surface exists to map. Tests a different side of Monarch's mapping.Later

5.2 How much of Monarch is under test?

Monarch works in three stages. A test can cover one, two or all three:

StageWhat it does
1. DiscoveryMonarch explores the platform and builds its knowledge base: which actions exist, which API calls they need, what they do and do not do.
2. Workflow creationMonarch's agent turns the user's request into a workflow, using that knowledge base.
3. Workflow executionMonarch's engine runs the workflow: makes the API calls, handles errors, retries.

So there are three ways to test Monarch, and all three are worth having:

  • Full flow (1 + 2 + 3): Monarch discovers the platform itself, then creates and runs the workflow. This is the real product story.
  • Create and run (2 + 3): the knowledge base is given to Monarch; we measure how well it writes and runs workflows.
  • Run only (3): a correct workflow is given to Monarch; we measure only the engine.
Where Lucas's design stands: it covers "create and run" only, with the knowledge base loaded by hand from the 47 description files. Discovery is never exercised. Carlos's direction (2 Sep): for the first version, the target stays the simulated API set, and all three test modes get built against it, including the full flow where Monarch has to discover the mock API on its own.
Good news from the Monarch code: Feature Discovery can map a platform from an OpenAPI document alone, no UI needed (it already does this for Slack and Linear). So the full-flow mode is feasible on the mock: we publish an OpenAPI file for the 47 simulated apps and let Monarch discover it. The same mechanism also solves the knowledge-base problem in section 8.4 without inserting anything by hand.

6. The rules Lucas set

These come from the revised design document. They survived the review, or were created by it.

6.1 Fair comparison

  • Everyone gets the same task text and the same three tools. Monarch gets no extra knowledge that a raw model cannot reach.
  • Every task is frozen before any competitor runs: a hash of its prompt, starting data and checks is stored. Grading later against a changed task is refused.
  • Each task runs several times per competitor (k=4 in the simulation, k=2 against real apps) so we measure reliability, not luck.
  • Comparisons are paired: the same task, same trial number, competitor A vs competitor B. Wins and losses are counted; a standard statistical test says whether the difference is real.
  • Vendor agents are run with pinned versions and API-key billing. Any non-default setting is recorded next to the result.

6.2 Honest numbers

  • Every number in a report carries its source: which task set, which version, how many results, which competitor, which run. No number is typed by hand.
  • Cost includes every token spent, split into cached and non-cached, priced from a versioned price table. Time is measured per stage.
  • Infrastructure failures (rate limits, model down) are counted separately and never as a competitor failure.

6.3 What may be published

Three levels, decided by Sam:

  1. Internal only. Everything, every competitor, real dollars. This is what we build now.
  2. Public progress. Monarch compared with earlier Monarch versions, plus an open description of the method. No vendor is named.
  3. Public comparison naming vendors. Only if a neutral third party governs it. Otherwise a Monarch-branded leaderboard naming Claude Code or Codex is not credible and hurts partnerships.

The report generator enforces this in code: a public report physically cannot contain a raw-model or experimental-Monarch result.

6.5 Things deliberately left out for now

  • Running the whole task set against real apps (estimated at six figures in cost).
  • Publishing exact dollar costs externally (ratios only).
  • A public brand name for the benchmark.
  • Adopting an off-the-shelf benchmark framework. Lucas evaluated one ("Harbor") and kept only its small adapter layer.

8. What we learned from the Monarch code

Read on 2 Sep 2026 in the ../monarch repository.

8.1 Which model Monarch uses

Workflow creation runs on the Claude Agent SDK over AWS Bedrock, and it is a team of models, not one:

RoleModel
Main brain that writes the workflowClaude Opus 4.8, highest effort setting
Picks candidate actions, first-pass triage, advisory checksClaude Haiku 4.5
Criticizes the planClaude Sonnet 5
Final reviewClaude Sonnet 4.6
Investigates failed runsClaude Opus 5
Decision steps inside a running workflowHaiku 4.5 or Sonnet 5

The engine that makes the actual API calls uses no model at all. Fable and Mythos are blocked in Monarch by a data-retention decision.

What this means for the benchmark: the fair baseline is raw Claude Opus 4.8, because that is Monarch's own brain. The benchmark does not have a Claude adapter yet. And Monarch's cost per task must add up the whole team of models, not just the main one.

8.2 MCP or HTTP? HTTP.

The engine calls apps with plain HTTP requests (or through a browser, or SQL, depending on the action). It never uses MCP at run time. So the simulated apps need a small HTTP front door. Lucas already sketched it (wb_arms/http_shim.py).

8.3 Driving Monarch without the UI

Possible, but only through HTTP endpoints that require a logged-in session. There is no command line and no API key for this:

POST /api/workflows/recipe/runs      { goal: "..." }      create a workflow from text
GET  /api/workflows/recipe/runs/:id/stream                progress (server-sent events)
POST /api/workflows/:id/run          { mode: "live" }     run a saved workflow

To run this, the whole Monarch stack must be up: Postgres, LocalStack (queues, DynamoDB, a Lambda emulator that needs Docker's socket), the backend, the workflow orchestrator, the ingest worker, and the Feature Discovery API.

8.4 The knowledge base problem

Monarch's workflow agent does not read a file. It asks the Feature Discovery service over HTTP, which reads from Postgres. The file Lucas generates from the 47 app descriptions has nowhere to go.

Two supported ways to get the simulated apps into Feature Discovery, both documented in feature-discovery/docs/public-api-seeds-runbook.md:

  • Discovery from an OpenAPI document. Register an "api_spec" discovery configuration with no credential and a URL to an OpenAPI file. Monarch's discovery reads the spec and writes the knowledge base itself. This is how the full-flow test mode works.
  • Seed fixtures. A small generator script turns a spec into fixture files that are loaded as a seed. Deterministic and reviewable. This is how the "create and run" mode gets a fixed, known knowledge base.

Either way, we need one thing we do not have yet: an OpenAPI document for the 47 simulated apps, generated from the same 47 description files, and served by the HTTP front door.

8.5 Tracking already in Monarch

  • OpenTelemetry, exporting to SigNoz.
  • A second, filtered export of model calls to Langfuse, switched on by two environment variables.
  • Token counts per model call, and a per-run ledger of tokens for workflow creation.
  • No dollar cost anywhere on the product side. Only Feature Discovery has a price table.

Monarch does not emit the event file Lucas's benchmark expects. Either the benchmark reads Monarch's run records instead, or Monarch gets per-stage tracking added (planned, see PLAN.md).

15. Words used in this project

Arm / competitor
One thing being measured: a model, an agent, or Monarch, with a fixed configuration.
Episode / test
One task run once by one competitor.
Pass (strict)
Expected result present, nothing else changed, and the competitor finished normally.
pass^k
Chance that k runs of the same task all pass. A reliability score.
Source line
The provenance attached to every number: task set, version, count, competitor, run.
Contract hash
Fingerprint of a task (prompt + starting data + checks), frozen before any run.
Stock
"As shipped": pinned version, all settings recorded.
Synthetic / simulated mode
Running against the AutomationBench mock apps.
Real mode
Running against real accounts on real platforms.
AutomationBench
Zapier's open-source benchmark: 47 simulated apps and 576 tasks. We reuse its apps and tasks.
Feature Discovery
The part of Monarch that maps a platform and stores what it found (Postgres). The workflow agent reads from it.
Business Action
One operation on one platform in Monarch's knowledge base, with the HTTP (or browser, or SQL) call behind it.
Recipe
Monarch's internal name for a workflow written by its agent.
